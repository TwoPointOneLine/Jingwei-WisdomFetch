## 一、产品概述

**精卫（Jingwei WisdomFetch，缩写 JWF）** 是一款面向普通用户的**金融智能知识库系统**——基于业界成熟的检索增强生成（RAG, Retrieval-Augmented Generation）范式构建，帮助用户从浩如烟海的金融文档中，像聊天一样获取**有依据、可追溯、不编造**的答案。

用户无需知道资料存放在哪里，也无需手动翻阅大量产品说明书、公告、研报或问答文档。只需用自然语言提问，精卫即从已构建的知识库中**先检索、后生成**：检索相关资料片段，结合上下文生成回答，并**标注可追溯的来源**。

> 行业背景：据 2025–2026 年企业 RAG 实践综述，RAG 通过将"通用大模型"与"企业私有知识"连接，使回答准确率较纯大模型方案显著提升，已成为金融、医疗、法律等强合规垂直领域落地智能问答的主流架构。精卫即这一范式在金融知识查询场景的工程化产品。

**产品定位（不可突破的约束）**：金融知识查询与资料理解工具——**不提供个性化投资建议、不承诺收益、不替代正式产品文件或人工专业判断**。

## 二、产品定位与价值

### 目标用户

- 希望读懂产品条款、风险等级、申赎规则的**普通投资者**；
- 需要快速读懂公告、研报、政策的**金融从业者**；
- 需要统一知识管理能力的**金融机构内部团队**。

### 核心价值

1. **降低理解门槛**：用通俗语言解释专业条款与术语。
2. **答案有据可查**：每条回答标注来源，可回溯原文（RAG 范式的天然优势）。
3. **合规安全可靠**：不荐股、不承诺收益，风险提示严谨，无资料不编造。
4. **对话式体验**：自然语言提问、多轮追问、流式输出。
5. **私有化可控**：支持机构内网部署，资料与问答数据不出域，满足金融数据合规。

## 三、为什么是 RAG —— 技术理念（非实现细节）

精卫采用"先检索、后生成"的 RAG 范式，而非让大模型自由发挥。这一选择源于金融场景的硬性要求：

| 理念 | 说明 | 带来的价值 |
| :--- | :--- | :--- |
| 知识锚定 | 答案基于检索到的权威资料生成，而非模型记忆 | 抑制"幻觉"，事实可溯源 |
| 私有数据连接 | 将机构自有文档接入模型，弥补通用模型的知识盲区 | 回答贴合本机构产品与口径 |
| 可引用可回溯 | 每段回答对应具体资料片段与来源 | 用户可核验，满足留痕要求 |
| 不脱离资料 | 资料未覆盖时明确拒答，不臆测 | 杜绝编造数据/条款/结论 |

> 行业实践表明，RAG 知识库的标准链路为：文档导入 → 智能解析与分段 → 向量化存储 → 语义检索与重排（Rerank）→ 基于检索结果生成。精卫的能力设计即围绕这一链路展开（详见第四章）。

## 四、核心能力

精卫的能力由四大引擎支撑，共同保证"准确、可追溯、不编造"：

| 引擎 | 命名 | 说明 |
| :--- | :--- | :--- |
| 知识构建 | **精卫衔文** | 多类型金融文档导入、解析、切分与向量化入库 |
| 智能问答 | **精卫问答** | 基于 RAG 的检索增强问答，先检索后生成 |
| 引用溯源 | **精卫引源** | 每条回答标注来源文件、条目、发布时间，可回溯原文 |
| 合规护栏 | **精卫守正** | 风险提示严谨、禁用收益承诺话术、无资料时拒答不编造 |

**关键能力点**

- **检索增强（RAG）**：回答锚定知识库内容，从源头降低编造风险。
- **来源溯源**：回答与引用片段一一对应，用户可核验原始资料。
- **流式输出**：回答实时逐字呈现，交互顺畅。
- **多轮追问**：基于会话上下文理解连续提问，聚焦同一主题深入。
- **会话隔离**：未登录访客按设备隔离，登录用户按账号隔离，登录后历史自动归并、不丢失。

## 五、功能体系

### 5.1 查询能力覆盖

支持查询以下类型金融资料并基于内容作答：

- 金融产品资料、产品说明书、产品风险揭示书；
- 基金招募说明书、基金产品资料概要；
- 理财产品说明书、业务流程说明；
- 市场资讯、行业分析、宏观政策与研究资料；
- 公司公告摘要、政策解读资料；
- 金融术语解释、常见问题 FAQ、风险提示材料。

### 5.2 能力清单

| 能力 | 说明 | 典型问题 |
| :--- | :--- | :--- |
| 金融产品问答 | 产品基本信息、投资方向、风险等级、申赎规则、费用与收益分配、适合人群 | "帮我介绍一下 XX 基金" |
| 金融知识问答 | 用通俗语言解释金融概念，避免过度专业化 | "什么是净值型理财？" |
| 市场资讯查询 | 基于已导入资料总结观点；不脱离资料自行编造结论 | "近期宏观政策对市场有何影响？" |
| 公司公告查询 | 返回公告核心内容，附名称、时间与来源；无则明确提示 | "这份公告主要讲了什么？" |
| 风险提示查询 | 谨慎、客观提示风险，引导结合承受能力判断 | "这个理财产品有什么风险？" |
| 常见业务问答 | 覆盖开户、申购、赎回、到账、手续费、风险测评等业务规则 | "基金赎回多久到账？" |

### 5.3 典型场景

| 场景 | 用户提问 | 系统返回 |
| :--- | :--- | :--- |
| 查询产品 | 帮我介绍一下 XX 基金 | 基本信息、投资方向、风险等级、费用/申赎、主要风险、来源 |
| 查询风险 | 这个理财产品有什么风险？ | 本金亏损、收益波动、流动性/市场/信用风险等 + 承受能力提示 |
| 查询概念 | 什么是净值型理财？ | 通俗解释 + 注意事项 + 引用来源 |
| 查询公告 | 这份公告主要讲了什么？ | 核心内容总结 + 名称/时间/来源；无则提示 |
| 多轮追问 | 风险高吗？/ 适合稳健型吗？ | 基于上下文理解同一对象，继续基于资料作答 |
| 无资料拒答 | 超出知识库范围 | 标准话术，不编造 |

## 六、知识库内容规范

### 6.1 可导入内容

金融产品资料、说明书、风险揭示书、招募说明书、产品资料概要、理财产品说明书、市场资讯、行业分析、公告摘要、政策解读、术语解释、风险提示、FAQ、业务流程说明。

## 七、回答要求

### 7.1 回答结构

简要结论 → 主要内容（分点）→ 风险提示 → 注意事项 → 引用来源（资料名称、内容类型、产品名称/代码、发布时间、来源文件）。

### 7.2 无资料时的回答

> 当前知识库中未检索到足够信息，建议查看正式产品文件、公告原文或咨询相关工作人员。

系统不应为回答问题而编造数据、公告内容、产品条款或市场结论。

## 八、风险与合规边界

> 背景：2025 年多家媒体实测显示，通用大模型在金融场景下"荐股""直给股票代码"已引发监管与法律争议；部分合规平台（如大智慧"慧搜"）对荐股提问直接拒绝并提示风险。精卫从产品设计之初即把"不荐股、不承诺收益"作为刚性边界，而非事后补救。

| 合规原则 | 说明 |
| :--- | :--- |
| 不提供投资建议 | 只提供知识查询与资料解释，不指导买入/卖出/持有/赎回 |
| 不承诺收益 | 禁用"一定赚钱""保证收益""保本无风险""稳赚不赔"等表达 |
| 风险提示谨慎 | 提示"金融产品存在风险""历史业绩不代表未来表现""投资需结合自身风险承受能力" |
| 不保证实时性 | 涉及最新行情/净值/公告时，提示用户查看官方渠道或实时数据源 |
| 数据不出域 | 支持私有化部署，资料与问答数据留存于机构自有环境 |
| 可标识可投诉 | 对 AI 生成内容提供来源标识与用户纠错反馈渠道（参照《生成式人工智能服务管理暂行办法》） |

## 十二、部署与数据安全（需求视角）

- 支持**私有化部署**于机构自有环境，资料与问答数据不出域；
- 支持按角色进行身份与权限管理（管理员 / 普通用户 / 访客）；
- 多用户数据按账号隔离，访客按设备隔离；
- 关键操作可审计留痕，满足金融机构适当性管理与数据安全要求；
- 提供清晰部署指引与健康检查能力，便于运维监控。

> 具体技术选型与部署形态由实施团队在满足上述需求的前提下确定。
